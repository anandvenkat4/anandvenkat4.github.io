Advanced reasoning — buying reliability with compute

Day 1 was about asking well. Today is about what to do when asking well still isn't enough — and how to justify the extra cost.
Start here · the uncomfortable demo

The same prompt, run twice, two different answers

Yesterday you learned to write a clear prompt. Here is the thing nobody tells you: a good prompt run twice can give you two different answers. Not because the model is broken — because sampling is random.

If your prompt is right 70% of the time, you do not have a 70%-accurate system. You have a system that is wrong in a way you cannot predict. Every technique today exists to attack that.

The trade is always the same: more tokens, more reliability. Your job is to decide when that trade is worth paying for.

Self-consistency — sample, then vote

If a single run is unreliable, run it several times and take the majority. It feels almost too simple, and it works: Wang et al., 2022 reported double-digit gains on reasoning benchmarks from voting alone.

Sample the model below. Watch individual runs disagree — then watch the vote settle.

live Sample and vote
Needs temperature > 0At temperature 0 every sample is identical and voting is pointless. Diversity is the mechanism.
Use odd numbers3, 5 or 7 samples. Even numbers can tie.
It reduces variance, not biasIf the model is wrong on average, voting confidently returns the wrong answer. This is the limitation to say out loud in a viva.
Needs a comparable answerYou can vote on "Rs 4". You cannot vote on three different paragraphs of prose.

Decomposition — make failure visible

Instead of one prompt doing five things, use five prompts doing one thing each, feeding forward. Least-to-most prompting (Zhou et al., 2022) does exactly this.

The accuracy gain is real but secondary. The real prize is debuggability: when a chain fails you can see which link broke. When a single mega-prompt fails, you get one wrong number and no clue.

Lab 5 · 55 minutes

Make an unreliable prompt reliable — and prove it

Take a task your model gets wrong some of the time. Apply decomposition or self-consistency. Measure before and after on 5–8 items.

  • Done = a before/after accuracy number on the same test items, plus both prompts.
  • Break it: find a task where the technique makes things worse. They exist, and finding one is worth more than another success.
  • Stretch: add a self-critique pass and check whether it actually helped or just sounded better.
